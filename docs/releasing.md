# Releasing

| Piece | Tool | Config |
| ---- | ---- | ---- |
| Version, changelog, `vX.Y.Z` tag | [release-plz](https://release-plz.dev) | `release-plz.toml`, `.github/workflows/release-plz.yml` |
| Sponsor bundle, checksums, GitHub Release | [dist](https://github.com/axodotdev/cargo-dist) | `dist-workspace.toml`, `.github/workflows/release.yml` (generated by `scripts/dist-generate.sh`), `.github/workflows/build-sponsor.yml` |
| Hosted verifier image | CI | `.github/workflows/ci.yml` ([details](../native/linux-amd64-build.md)) |

The released product is `concurro-relay`, the Sponsor. Every crate inherits the workspace
version, so all of them move with it. Nothing is published to crates.io; release-plz reads the
latest version from `v*` tags.

## Flow

1. A push to `main` that changes `concurro-relay` or a crate it ships opens or updates the
   release PR (label `release`), authored by Concurro Release Bot. The PR bumps the workspace
   version and adds a `CHANGELOG.md` entry from those commits.
2. Edit the PR before merging: tidy the changelog entry, which leaves out commits outside
   the crates such as `native/` or `patches/`, and pick the version. release-plz bumps the
   patch version for plain commits; for another version, edit `[workspace.package]` `version`
   in `Cargo.toml` and run `cargo update --workspace`. Don't use `release-plz set-version`: it
   replaces each crate's `version.workspace = true` with a literal version.
3. Merging it creates the tag and dispatches `release.yml` for it. No workflow runs on tag
   pushes; the dispatch starts the build.
4. In `release.yml`, dist plans the release and calls `build-sponsor.yml`, which has one job
   per target. Each job builds the native runtime from source, packages both roles
   (`native/package.py`) and archives the Sponsor package (`native/release.py`). It then
   installs the archive as below and tests the installed bundle offline.
   - **macOS arm64:** `native/build_macos_arm64.sh` on `macos-15`; the offline bootstrap test.
   - **Linux x86-64:** `native/build_linux_amd64.sh` in the Debian 13 builder container on
     `ubuntu-24.04`. `native/test_linux_amd64.sh` installs the archive in a clean Ubuntu 24.04
     container. It checks that every packaged image loads only packaged libraries or glibc,
     then runs the offline bootstrap tests (Codex and Claude HTTP/2) and two request proofs.

   dist adds the source tarball and `sha256.sum`, then creates the GitHub Release with the
   version's `CHANGELOG.md` section as notes.

release-plz builds the release PR in a copy of the checkout that leaves out gitignored paths,
where `cargo update` would miss `upstream/`. So the job first runs
`scripts/release-pr-checkout.sh`. It moves the `upstream/` ignore rule into a
`core.excludesFile` that it passes to later steps through git's environment
(`GIT_CONFIG_COUNT`). The copy then includes the sources, and git still keeps them out of the
release commit. The workaround depends on release-plz internals, so after changing the pinned
release-plz version, rerun its validation: release-pr must get past `cargo update`, and the
commit must contain only the version and changelog files.

The release PR changes only the version and the changelog. CI runs on it like on any PR,
including `dist plan`. Nothing approves or merges it automatically; it is reviewed and merged
by hand.

### Releasing changes outside the crates

release-plz detects changes only inside a crate's directory. A change to `native/`,
`patches/` or other bundle inputs alone opens no release PR; it is not detected
automatically. Release it with a normal reviewed PR that sets the version and changelog:

- If a release PR is open, add the change to its changelog entry.
- Otherwise open a PR from a branch named `release-plz-<anything>`. Bump
  `[workspace.package]` `version` in `Cargo.toml`, run `cargo update --workspace`, and add the
  version's `CHANGELOG.md` section. Review and merge it; release-plz treats a merged
  `release-plz-` branch PR as a release PR, so step 3 follows.

release-plz treats every open `release-plz-` PR as its release PR. If a crate change lands
while yours is open, it closes yours (the branch stays) and opens its own; carry the entry
over to that one.

To build or release by hand:

```bash
gh workflow run release.yml -f tag=dry-run                  # build and test; publish nothing
gh workflow run release.yml --ref v0.1.0 -f tag=v0.1.0      # release an existing tag
```

## Protocol 6 release

The Antigravity and shared gzip changes require protocol 6 Sponsors. Publish the Sponsor
bundle and verifier from the same reviewed relay revision. Upgrade devices before enabling
the verifier; older clients receive the protocol upgrade refusal. Pin Concurro's
`concurro-relay-hosted-api` dependency to that release, then release the service, launcher
and Backoffice with their Google migrations. Verify both Claude and Antigravity dispatch
with the new Sponsor. Google's default destination is
`daily-cloudcode-pa.googleapis.com:443`.

## Protocol 5 release

Sponsor 0.1.2 introduced relay protocol 5. To deploy it:

1. Install Sponsor 0.1.2 or later on any device that will pair or serve work.
   Protocol 4 clients receive the existing update message.
2. Resolve the `v0.1.2` tag to its full commit SHA. Check CI and the published
   verifier image for that SHA and use it as the deployment pin. Use the same
   Git tag for the `concurro-relay-hosted-api` dependency in Concurro.
3. Provision the three distinct [verifier bearers and exchange public keys](../README.md#hosted-verifier).
   Mount the existing registry and the claim journal on durable storage. Activate
   sponsorship with the Accounts owner API, Gateway signed dispatch and Exchange
   claim issuer and release caller in place. The previous Vault/Exchange HTTP
   endpoints and shared verifier token were removed.
4. Verify pairing and a subscription dispatch with a protocol 5 Sponsor after
   the new callers are connected.

## The Sponsor bundle and installing it

| Target | Archive | Runs on |
| ---- | ---- | ---- |
| `aarch64-apple-darwin` | `concurro-relay-aarch64-apple-darwin.tar.gz` | macOS on Apple Silicon |
| `x86_64-unknown-linux-gnu` | `concurro-relay-x86_64-unknown-linux-gnu.tar.gz` | Linux x86-64 with glibc 2.38 or newer and an x86-64-v3 CPU with AES and PCLMUL; tested on Ubuntu 24.04 |

Each archive holds one directory:

- `bin/concurro-relay`;
- `native-runtime/`: the native worker, DiStefano and MP-SPDZ helpers, request-proof,
  OpenSSL, their shared libraries and the public circuits;
- `manifest.json` (file hashes; on Linux also the glibc version it requires) and
  `release.json` (version, commit, platform);
- `licenses/`: third-party notices, with `third-party.json` recording where each component
  came from (`licenses/README.md` explains the layout):
  - **System libraries:** Debian package or Homebrew formula and version, plus its copyright
    or license files and Homebrew SBOM.
  - **Native helpers:** the upstream git checkouts, by URL and commit, plus their license
    files and the concurro-relay paths holding Concurro's changes (`modified_by`).
  - **Rust crates:** those compiled into the binaries, by version and source, plus their
    license files.

  Components whose upstream has no license file are listed with no notices.

On Linux, every library except glibc's own is in `native-runtime/lib`, found through
`$ORIGIN`-relative runpaths. The helpers are built for x86-64-v3 (AVX2, BMI2, FMA, LZCNT,
MOVBE) and also use AES-NI and PCLMULQDQ.

- **glibc 2.38 floor.** This is derived from the binaries' ELF version needs, not from a run
  on glibc 2.38. The helpers and bundled libraries, built on Debian 13, need GLIBC_2.38. The
  relay and worker also reference GLIBC_2.39 (`pidfd_spawnp`, `pidfd_getpid`) as a weak
  version need, which the loader tolerates. On glibc 2.38 it prints a harmless
  `weak version 'GLIBC_2.39' not found` line when they start.
- **Tested:** the release build installs and tests the archive on Ubuntu 24.04 (glibc 2.39).

Each archive has a `<archive>-third-party-sources.tar.gz` asset beside it, with its
`.sha256`. It holds the exact sources of the shipped copyleft libraries (`COPYLEFT` in
`native/notices.py`):

- **Linux:** the Debian source packages of GMP and of GCC's libstdc++ and libgcc_s, at the
  installed versions, from the signed Debian archive.
- **macOS:** GMP's source tarball as recorded in the Homebrew keg's SBOM, verified against
  its SHA-256.

The relay finds `native-runtime/` beside its `bin/`. dist's shell and Homebrew installers
install only executables, so dist generates no installer. Install on macOS with:

```bash
curl -fLO https://github.com/concurro/concurro-relay/releases/latest/download/concurro-relay-aarch64-apple-darwin.tar.gz
curl -fLO https://github.com/concurro/concurro-relay/releases/latest/download/concurro-relay-aarch64-apple-darwin.tar.gz.sha256
shasum -a 256 -c concurro-relay-aarch64-apple-darwin.tar.gz.sha256
mkdir -p ~/.local/opt && tar -xzf concurro-relay-aarch64-apple-darwin.tar.gz -C ~/.local/opt
export PATH="$HOME/.local/opt/concurro-relay-aarch64-apple-darwin/bin:$PATH"
```

On Linux:

```bash
curl -fLO https://github.com/concurro/concurro-relay/releases/latest/download/concurro-relay-x86_64-unknown-linux-gnu.tar.gz
curl -fLO https://github.com/concurro/concurro-relay/releases/latest/download/concurro-relay-x86_64-unknown-linux-gnu.tar.gz.sha256
sha256sum -c concurro-relay-x86_64-unknown-linux-gnu.tar.gz.sha256
mkdir -p ~/.local/opt && tar -xzf concurro-relay-x86_64-unknown-linux-gnu.tar.gz -C ~/.local/opt
export PATH="$HOME/.local/opt/concurro-relay-x86_64-unknown-linux-gnu/bin:$PATH"
```

Put the directory on `PATH` rather than symlinking the executable elsewhere: the relay locates
the bundle from its own path. The macOS packages are ad hoc signed, not notarized; a browser
download is quarantined by Gatekeeper, and `curl` is not.

## Requirements

- **Concurro Release Bot**, below: the release workflow's GitHub identity.
- **Build dependencies on the macOS runner:** Homebrew `cmake boost gmp libsodium openssl`,
  and Go (pinned with `actions/setup-go`) for BoringSSL.
- **On the Linux runner:** Docker. The builder (`native/Dockerfile.amd64-builder`) and the
  clean Ubuntu 24.04 test image are pinned by digest. The runner's CPU must be x86-64-v3 with
  AES and PCLMUL to run the tests.

### Concurro Release Bot

The organization does not let GitHub Actions create pull requests, so `release-plz.yml` acts
as a dedicated GitHub App. Each job mints a short-lived installation token for this repository
only, with the job's permissions below. dist (`release.yml`, `build-sponsor.yml`) and CI keep
the job-scoped `GITHUB_TOKEN`.

| Job | Contents | Pull requests | Actions |
| ---- | ---- | ---- | ---- |
| Release PR (branch, commit, PR, `release` label) | write | write | — |
| Release (find the merged release PR, tag, dispatch `release.yml`) | write | read | write |

To set it up (organization owner):

1. *Organization settings → Developer settings → GitHub Apps → New GitHub App*.
   - Name `Concurro Release Bot`; homepage URL
     `https://github.com/concurro/concurro-relay`.
   - Webhook: clear **Active**. Nothing listens for events.
   - Repository permissions: **Contents** read and write, **Pull requests** read and write,
     **Actions** read and write. **Metadata** read-only is added automatically. Leave every
     other repository, organization and account permission at *No access*.
   - Subscribe to no events.
   - *Where can this GitHub App be installed?* **Only on this account**.
2. *Install App* → `concurro` → **Only select repositories** → `concurro-relay`.
3. In the App's settings, copy the **Client ID** and generate a private key. Store both in
   *concurro-relay → Settings → Secrets and variables → Actions*:
   - variable `RELEASE_BOT_CLIENT_ID`: the Client ID (not secret);
   - secret `RELEASE_BOT_PRIVATE_KEY`: the entire `.pem` file.

   Then delete the downloaded `.pem` file; GitHub keeps only the public key.

The App bypasses no branch or tag rule, approves nothing and merges nothing. To rotate the
key, generate a new one, update the secret, then delete the old key in the App's settings.

## Changing the dist config

Edit `dist-workspace.toml`, then regenerate the workflow with the same dist version as
`cargo-dist-version`. Actions are pinned by `[dist.github-action-commits]`.

`release.yml` is dist's output plus one step. The `plan`, `build-global-artifacts` and `host`
jobs run `scripts/upstream.sh` after their checkout, because dist reads the full cargo metadata
there and the `[patch]` table points into `upstream/`. dist has no setup hook for those jobs;
`github-build-setup` reaches only `build-local-artifacts`, which is disabled. So
`allow-dirty = ["ci"]` lets dist accept the step, and `scripts/dist-generate.sh` regenerates
the workflow in place of `dist generate`.

```bash
cargo install --locked cargo-dist@0.34.0
./scripts/upstream.sh            # once; dist needs it for cargo metadata
scripts/dist-generate.sh         # regenerate release.yml
scripts/dist-generate.sh --check # fails if release.yml differs; changes nothing
dist plan                        # one app, one target, one archive
```
